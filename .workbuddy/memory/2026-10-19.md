# 2026-10-19 工作日志

## 新增数据快照邮件推送 workflow

- 新文件 `.github/workflows/data-mail.yml`（name: Mail Data Snapshot），每天 07:00 UTC
  把 `scabase-fetcher/data/` 打包成 `scabase-data-YYYYMMDD.tar.gz` 发到
  `luweb@foxmail.com`（workflow env `DEFAULT_TO`，可用 secret `MAIL_TO` 覆盖）。
- 时间选择理由：采集窗口为 02:00 漏洞 / 03:17 社区健康 / 05:43 软件漏洞，
  07:00 排在全部之后才不会漏掉当天最后一次采集。
- 体积：原始 11MB → gzip 后约 1.3MB，附件发送无压力；阈值设 20MB，
  超限降级为「上传 artifact + 邮件内给下载链接」，避免被退信。
- 打包排除 `facts/`（事实层中间产物，已 gitignore）。
- 发送用 `dawidd6/action-send-mail@v4`（v3 已过时，README 示例为 v4；仓库还有 v5 分支）。
  Secrets：MAIL_SERVER / MAIL_PORT / MAIL_USERNAME / MAIL_PASSWORD / MAIL_SECURE / MAIL_TO。
- 防噪设计：未配置 MAIL_SERVER/USERNAME/PASSWORD 时只上传 artifact 并打 warning，
  不置红（否则每天一个失败通知会掩盖真问题）。
- 邮件正文由内联 python 读 `scabase-fetcher/data/index.json` 生成 HTML + 纯文本
  （数据集清单 / 大小 / 更新频率 / 索引时间 / 站点 / 本次 run 链接），
  HTML 与 txt 都通过 `file://` 传给 action（multipart）。
- 附件同时 upload-artifact 留存 30 天（保留策略与邮件解耦）。
- 文档：`readme_zh_cn.md` 在「以包的形式分发数据（GitHub Packages）」后新增
  「每日数据快照邮件推送」小节，含 Secrets 表格与降级说明。
- 已本地验证：YAML 可解析、tar 打包产物清单正确、正文脚本输出正常、
  收件人优先级 INPUT_TO > MAIL_TO > DEFAULT_TO 三种组合均符合预期。
  未验证：真实 SMTP 发送（需用户先配置 secrets 后手动 Run workflow）。

## 健康度信号「获取不全」根因与修复（用户报：nginx fork/watch/]).-> 数据为空）
### 根因（两个叠加，都不是 GitHub API 本身的问题）
1. **GitHub 配额按小时窗口计的踩踏**：community-health 03:17 用满当小时配额，
   software-collect 03:43 落在同一窗口 → 403 后旧逻辑只退避几秒就「降级」，
   65 个软件只剩 23 个有 stars、0 个 forks/watchers。已实测 GitHub API 正常
   （nginx/nginx：star 31910 / fork 8317 / watch 957 / pushed_at 2 天前）。
2. **并发工作流 push 被拒丢数据**：10-18 那轮 software-collect 采集成功却在
   「提交数据更新」步 failed（non-fast-forward，与 community-health 撞车），
   外部只看到「数据一直是旧的」。

### 修复落地（已推送并触发补采）
- `fetch_oss_health._rate_limit_sleep()`：按 X-RateLimit-Reset 睡到配额重置再续跑，
  预算 `SCABASE_GH_WAIT_BUDGET`（默认 1800s，0 可关），_head_status 同理。
- `fetch_oss_health.repo_status()`：ok / not_found / unknown —— 区分「仓库失效」
  与「本轮被限流」。**GitLab 案例**：gitlab-org/gitlab 现已 404（源码迁出自有
  实例），信号全空，前端此前只显示一堆「未知」。
- `fetch_software --no-vulns`：只刷 GitHub 信号，跳过 NVD 与其 6.5s 间隔，
  且不再重写 software-vulns.json（避免 7MB 无意义 diff）。
- 新增 `.github/workflows/refresh-health-signals.yml`：手动补采通道
  （Run workflow），先补软件维度再 REST dispatch community-health（串行）。
  曾加 push(paths: 自身) 触发器，结果一次推送触发多个实例互抢配额 → 已移除。
- 4 个工作流的 push 段统一改为 fetch + rebase + 冲突重算 index.json + 重试 3 次；
  tests/test_workflows.py 新增 test_data_push_is_conflict_safe 守着。
- 覆盖率门禁：software-collect 提交前要求 forks 覆盖 ≥90%，community-health ≥80%，
  否则失败并保留旧数据（避免拿坏数据覆盖好的）。
- 并发治理：community-health / software-collect / refresh-health-signals 各加
  concurrency group（cancel-in-progress: false）；**pages.yml 的
  cancel-in-progress 由 true 改 false** —— 数据连续提交时后到的部署会取消前一个
  并记为 failure（Deploy to GitHub Pages failure），改为排队串行。
- software-collect cron 03:43 → **05:43**（跨过配额窗口）。
