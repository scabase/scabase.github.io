Background

开源治理的三个断层

Gap 01

查得到，管不住

扫描出了 CVE 清单，却没有准入决策。高危组件照样进生产，报告在 KB 和 PPT 里躺灰。

无门禁无结论
Gap 02

看漏洞，不看活不活

只统计 CVE 数量，不评估维护可持续性。两年后停止维护的组件，出事时无人修。

bus factor停维护
Gap 03

外网有数据，内网不可用

情报工具假设「能连公网」。隔离网里只能人工搬运 Excel，数据无法核验、无法保证新鲜。

离线不可验签
漏洞只是风险的一个切面 —— 「这个组件三年后还有人维护吗」同样是安全问题。
Architecture

互联网采集，内网管控，中间只有数据包

Zone A · 互联网 允许出站

采集与富化
  1. 采集 OSV / NVD / KEV / EPSS漏洞情报与利用热度
  2. 采集活跃度 / 许可证GitHub、deps.dev、npm / PyPI registry
  3. 归一化到 PURL 事实层按数据集分片存储
  4. 构建 + 签名 Bundlemanifest + 逐文件 sha256
单向摆渡
▶

Zone B · 内网 禁止出站

评估与管控
  1. 验签 + 原子导入失败拒绝，回滚要好于半吊子更新
  2. 摄入应用 SBOM / 资产台账CI 上报，维护应用群组
  3. 引入前门禁 / 群组评估四维评分 + 硬阻断
  4. 脱敏回执 → 反向摆渡仅含 seq、水位、计数
PURL 为主键
漏洞 / 活跃度 / 许可证 / 资产挂在同一主键上
内网零公网请求
未知组件显式「数据缺失」，不静默补全
信任工程化
签名 + seq 链 + 哈希校验，而非口头声明

硬阻断（直接 Deny）

  • KEV 且无修复版本
  • CVSS ≥ 9.0 且无修复版本
  • 许可证与用途冲突
  • 已 archived / deprecated

诚实的不确定性

数据陈旧时置信度下降 → 分值向保守方向调整，并强制降级为人工复核；策略可配 staleness_as_deny 直接判 Deny。

AllowconditionReviewDenyException
样例：pkg:maven/com.alibaba/fastjson@1.2.24 → CVSS 10.0 打底 25 分 + 2 条暴露超 180 天 +3 → 漏洞维度 28.0 / 35， health 无信号时不假装健康，按保守值计分、置信度标 0、结论降级为人工复核。
Capability 05

不产 SBOM，也能直接扫

  • 读项目本来就有的文件：不要求业务侧先产出 SBOM，降低推行阻力
  • 直接 / 传递依赖自动区分，归一为 PURL
  • 保留 version_req 与 pinned：没锁版本本身就是风险信号
  • --app 直接生成含 purls / gavs 的资产台账条目
解析不出任何组件时以退出码 2 失败 —— 门禁绝不静默放行。

Capability 06

AI 可以参与，但必须能被验证

Step 1

安全基线目录

内置 32 条，覆盖独立部署型（Redis、Nginx、Tomcat、Kafka、ZooKeeper、Elasticsearch、Nacos、MySQL、MongoDB、RabbitMQ、Docker、Jenkins）与依赖引入型（fastjson、log4j、Shiro、Struts、Spring Boot Actuator、XStream、Jackson）。

Step 2

AI 脚本生成

按目标平台规范产出：sreops 巡检脚本 / codescan 规则包 / 通用 Python 巡检。LLM 不可用或不通过校验 → 自动回落确定性模板，全程不发起外部请求。

Step 3

准确率回归

标注样本集回归校验，默认阈值 90%，不达标退出码非 0。产物写入 manifest.json，记录 sha256、生成方式（template / llm）与 review_required。

我们对 AI 的态度：可以参与生成，但要被静态检查、被标准样本集验收、被人工审核 —— 把「扫描准确率 90%」从口号变成流水线上的一道红绿灯。
Capability 07

从 CVE 到应用、到工单、到收敛证明

按应用聚合

影响面

受影响组件数、KEV 数、风险分、结论分布、基线待检项；漏洞命中精确到版本，不做粗粒度全包族告警。

工单定级

整改期限

按 KEV / CVSS 排序并定期限：critical 7 天 / high 15 / medium 30 / low 90，可直接派单到责任人。

增量对比

僵尸proof

以「应用 + 组件 + CVE」三元组输出新增 / 未修复 / 已闭环；跨 ≥2 个应用的高危组件列入共性风险。

群组分值口径

群组 = 0.6 × 最差组件 + 0.4 × 加权平均，避免平均值掩盖单点高危；同一组件出现在 ≥3 个应用且评分 ≥55 时列入共性风险。

为什么是三元组

只有 应用 × 组件 × CVE 才能证明「某一项风险这次真的闭环了」，而不是被总量平均稀释。

Capability 08

把「信任」做进协议，而不是写进 PPT

同步协议保障

  • manifest 签名：优先 ed25519，回落 HMAC-SHA256
  • 逐文件 sha256 + prev_digest 链 + seq 单调 → 防篡改、防回滚
  • 临时目录 + rename 原子切换，季度导入 snapshot 校准
  • 脱敏回执：仅含 seq、水位、计数，反向摆渡不带走内网应用信息

Engineering

做开源治理的项目，自己必须干净

E1

内网零依赖可跑

oss_intake/ 评分、同步、脚本生成、巡检路径纯 Python 标准库。

E2

自身依赖面最小

采集器仅 requests（固定 2.32.4）；前端纯 ES5 IIFE，无构建步骤。

E3

规范先行

全部能力用 OpenSpec 管理：基线 specs + changes 提案，每个 Requirement 至少一个 Scenario。

E4

自查不护短

self-scan 用本项目门禁引擎扫自身依赖，命中 Deny 即阻断；盲区以 warning 显式暴露。

E5

教学样本不污染

故意留下的漏洞样本加 .sample 后缀，避免被依赖图误认（曾因此多出 60 条假告警）。

E6

机器可读优先

llms.txt + index.json，WebFetch 直接取数，无需 Key、无跨域限制。

Rollout

三步落地，逐步加严

Step 1 · 看得见

先把现状摊开

Pages 或 docker compose up -d，把已有组件清单灌进去，先出一张 CVE 清单。不改造任何业务代码。

Step 2 · 管得住

把结论变成闸门

CI 里挂 gate，--fail-on deny 成为流水线的一道闸；同时产出 SARIF / JUnit / MR 评论。

Step 3 · 持续收敛

用增量证明

patrol 周期巡检 + 工单闭环，月度复盘看新增 / 未修复 / 已闭环三元组在朝哪边走。

Conclusion

开源治理的难点从来不是缺一个扫描器

而是 决策不可解释、数据不可核验、内网不可用。
ScaBase 把这三件事做成了默认能力。

决策可解释

白盒扣分制，每项都能追溯到依据

数据可核验

sha256 + 生成时间 + 来源链接

内网可用

零第三方依赖，单向摆渡
